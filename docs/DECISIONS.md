# TOIR — DECISIONS

Short log of decisions and why. Add a new entry only when a real decision is made. Newest at the bottom.

1. **Backend ownership:** FastAPI + PostgreSQL 16 + Docker Compose are the sole application backend.
2. **Data import:** historical hosted-service data is not migrated; only the normalized schema and relations are retained.
3. **One schema** (`postgres/schema.sql`): real foreign keys, no text links; work order repairs and items are separate tables (no JSONB). Statuses: `pending -> in_progress -> completed | cancelled`; `overdue` is computed from `date_end`, not stored.
4. **ТО intervals are a directory** (`maintenance_intervals`) edited by admin/operator in the UI. No hardcoded thresholds (no 5000...1600000 km, no "ТО-90").
5. **Auth:** own JWT. Access token 30 min, kept in memory. Refresh token 7 days in an httpOnly cookie, rotated, only its hash stored in DB. Login limiter: 5 failures -> 429 (in process memory for now; move to Redis/DB for production).
6. **Roles and scope:** admin, operator, master, management. Master sees only his own section; enforced on the server in the DB query; other sections return 404 before any status check. Deleting work orders: admin and management only.
7. **Server layout:** `docker compose -p toir` next to the production system "fuel"; backend on `127.0.0.1:8010`; Postgres not published; `deploy.sh` checks that fuel is unchanged. The server pulls through a read-only deploy key; the user pushes.
8. **Testing flow:** no Docker on the PC. Backend is tested by e2e scripts that the user runs on the server. Frontend is developed on the PC through an SSH tunnel to port 8010.
9. **Wialon:** ingest is a FastAPI endpoint protected by a token (replaces the old Express receiver).
10. **Work order number** `НЗ-YYYYMMDD-HHMMSS` is generated by the server; creation retries only on a number conflict.
11. **Localization:** supported locale tags are `uz-Latn`, `uz-Cyrl`, and `ru`; `ru` is the fallback. Locale is stored in a validated browser cookie. Canonical business names and IDs remain unchanged; normalized translation tables hold authored translations, and missing translations fall back to the canonical name with a missing flag. Existing user-entered free text is never auto-translated.
12. **Fixed-asset catalog behavior:** type/status codes remain stable keys; their authored labels are managed in the existing translation tables. Each status maps to one existing behavior (`operational`, `maintenance`, `repair`, `out_of_service`) so existing readiness rules remain explicit. Used catalog rows are deactivated, never hard-deleted; a used status cannot change behavior.
13. **Work-order detail data:** display only persisted work-order repair/item rows and linked TMC documents. Work-order item quantities are planned/requested quantities; TMC document quantities and prices retain their document meaning. Do not infer task completion, consumed/returned quantities, or change history because no such work-order tables/fields exist.
14. **Granular RBAC:** preserve role names (`admin`, `operator`, `master`, `management`) and keep `admin` as the immutable highest role. Permission catalog and per-role grants are database-backed, checked on each API request, and audited; only the initial setup may create an admin. Master section scope remains a separate backend data filter.
15. **User active status:** retain the existing `users.is_active` field; a dedicated `users.set_active` permission controls status changes. Deactivation rejects the actor's own account, protects the last active admin, invalidates access through the active-user lookup, and revokes all refresh tokens. No separate status audit table existed, so the UI does not attribute who changed the status.
16. **Work-order mileage snapshot:** use the existing server-written `work_orders.mileage_at_creation`; never backfill historical NULL values. Treat default asset mileage zero as unknown unless a mileage-history row confirms zero. Keep the linked asset immutable after order creation so the snapshot remains attributable. Do not claim a measurement source/time the schema does not capture; no migration is needed.
17. **List filtering:** apply search and business filters in backend repository queries, alongside existing permission/scope clauses. Keep sort fields whitelisted and query values bound. Add search indexes only after examining representative PostgreSQL plans; substring `ILIKE` may otherwise scan rows. Filter URL state is optional and must remain page-specific.
18. **Organizational hierarchy:** keep `sections` as the canonical unit table and preserve every existing `sections.id`; this avoids rewriting foreign keys in users, employees, assets, work orders, maintenance records, and TMC. Store authored `uz-Latn`, `uz-Cyrl`, and `ru` names in `section_translations`. Validate parent types and cycles in both API and PostgreSQL. Archive instead of hard-delete so historical references remain intact; run the read-only preflight against an isolated test copy before any migration. Keep the separate legacy `departments` table and its foreign keys unchanged until an authoritative department-to-unit mapping is supplied. Do not assume a safe downgrade: 0008 may reject duplicate names, 0007 downgrade drops hierarchy columns/data, and 0010 joins the hierarchy and permissions branches. Rehearse a branch-aware rollback against a disposable DB copy before proposing one.
19. **Wialon as a separate source:** keep fetched units in `wialon_units`; `fixed_assets` remains TOIR-owned. Join only by an explicitly assigned unique `fixed_assets.wialon_id`. Name/series/number comparisons may produce suggestions only and never create or change a link automatically. Master users must be limited to their own section and never receive Wialon-only rows in the unified asset view.
20. **GTK as a separate read-only source:** store GTK locomotives, carriages, trains, and observed membership history in GTK-only tables. Automatic GTK sync never writes or deletes TOIR `fixed_assets`; only separately requested, explicitly confirmed link and carriage-creation actions may do so. Close missing memberships instead of deleting history. A suspicious count drop skips all mirror updates until a later acceptable snapshot.
21. **GTK-to-asset links:** store only an explicitly operator-confirmed unique `fixed_assets.gtk_id`; matching by GTK ID, series, name, or number only suggests candidates and never links automatically. GTK remains a separate read-only source, and its rows do not enter the unified asset view or fixed-asset statistics.
22. **GTK mileage attribution baseline:** preserve GTK-imported `gtk_locomotives.checkpoint_mileage` as source data. Keep a separate per-locomotive TOIR mileage checkpoint; initialize/reset it when a locomotive link is first made or changed so no wagon mileage is attributed before the baseline.
23. **GTK migration drift:** migration `0013` was edited after it had already been applied in at least one environment; it must not be edited again. Alembic stores revision state, not a checksum of the migration body, so an applied database can differ from a fresh install and may not receive later objects or permission seeds. Verify affected databases before rollout and use a new forward migration for any correction.
24. **Canonical external asset links:** use `asset_source_links` as the source of truth for Wialon, GTK, Vesavoy, and OneC links, including active/ended history and uniqueness. Keep `fixed_assets.wialon_id` and `gtk_id` as compatibility mirrors only; link writes update both in one transaction, while application lookups use the canonical table.
25. **Passport organization unit:** map `fixed_assets.depot` only to an exact, unique active `sections.name`; do not infer a relation from `departments`. `sections` remains canonical, while `departments` is a separate legacy table with no authoritative mapping.
26. **Passport organization-unit assignment (P6):** the database facts supplied for the P6 audit report 86 `fixed_assets`, with `depot IS NULL` and `org_unit_id IS NULL` for all 86; therefore the existing exact-name backfill/report cannot infer any assignment. Keep `depot` unchanged, do not migrate or guess a mapping, and assign the canonical `org_unit_id` manually. The P6 bulk endpoint validates one active section, locks the selected assets in stable ID order, records every changed `org_unit_id` in `asset_field_changes`, and commits the batch atomically; its UI is deferred to P7. If later needed, an explicit `depot`-to-section mapping table is preferable to fuzzy name inference.
27. **P6 migration verification:** Alembic `env.py` supports offline mode, but revision `0018_asset_passport` performs Python backfill decisions by reading existing `fixed_assets` rows through `op.get_bind()`. Full `0012`→`0019` offline SQL rendering is therefore not a valid migration rehearsal; test the revision chain statically and rehearse the data-dependent upgrade/downgrade only against a disposable PostgreSQL copy.
28. **Legacy source mirror retirement:** do not drop `fixed_assets.gtk_id` or `wialon_id` before all compatibility readers/writers are removed. Remaining compatibility references include `FixedAsset` ORM/schema fields; fixed-asset create/PATCH validation, source linking, mirror writes, and GTK locomotive mileage checkpoint logic in `services/assets.py`; link mirror maintenance in `services/asset_links.py`; Wialon bootstrap-plan input/output; and request permission gates in `routers/assets.py`. GTK and Wialon source-object `gtk_id`/`wialon_id` identifiers in their mirror tables, APIs, adapters, and matching are source IDs, not the legacy fixed-asset columns. Retirement order: (1) compare active canonical links with legacy mirrors and resolve mismatches; (2) move all fixed-asset lookups and import/bootstrap consumers to `asset_source_links`; (3) stop accepting mirror fields on create/PATCH and keep dual-write for one compatibility window; (4) verify API/jobs and deployed clients no longer read them; (5) add a new forward migration to drop only the two mirror columns and update ORM/schema in that release. Preserve GTK/Wialon source-object IDs.
29. **P7 permission reconciliation:** keep the existing `role_permissions.granted` value as the database decision. The forward-only 0020 migration upserts the intended grants for asset links and conflicts, correcting existing rows without changing the 0008 default/override mechanism. The runtime database values were not queried during P7.
30. **Inventory import safety:** preview performs reads only and is not stored. Apply accepts resolved asset IDs from preview, rechecks assets and duplicate numbers under row locks, writes all accepted rows in one transaction, and relies on the existing unique constraints as the final race guard. Any commit integrity conflict rolls back the full import.
